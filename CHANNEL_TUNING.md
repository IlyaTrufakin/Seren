# Совместная настройка анализаторов на архиве

Это готовый офлайн-контур настройки будущих независимых анализаторов. Он использует основной ThreatEvaluator, не подключается к ПЛК и не передаёт архивные состояния рабочей системе. Сервер HTTP и живые отдельные анализаторы — следующий этап разделения приложения; эта часть их пока не запускает.

## Профиль канала

Начальные профили:
- `profiles/monitor1654/`
- `profiles/radar_kharkov/`

В каждом находятся `profile.json` (идентификация канала), `config.json` (его словари и правила), `criteria.json` (ожидаемые реакции). Это независимые копии нынешних настроек, а не утверждение, что каналы уже настроены правильно по месяцу истории. Ключи и телефон Telegram в копии отсутствуют. Рабочий `config_threats.json` не изменяется.

В отладчике выберите **Профиль / файлы → Открыть профиль канала**, откройте нужный `profile.json`, затем задайте архив и даты и нажмите «Анализировать».

Для запуска сразу с профилем:
```powershell
.\run_channel_debugger.bat --profile profiles/monitor1654
```

«Словари и правила» изменяет настройки в памяти. **Профиль / файлы → Сохранить настройки в профиль** фиксирует эксперимент; прежняя версия сохраняется в `revisions/`. Затем повторите анализ. Если настройки изменены мной через файлы, выберите **Перечитать профиль с диска** и повторите анализ. Проверка критериев откажется оценивать устаревший результат относительно изменённых настроек.

## Задание правильной реакции

Выберите сообщение и **Критерии → Задать ожидаемые уровни выбранного сообщения**. Укажите требуемый итоговый уровень и/или уровни отдельных типов. Пустое поле не проверяется, 0 явно означает отсутствие соответствующей угрозы. Ожидаемые уровни выбирает человек: они не подставляются автоматически из текущего результата.

Два набора: `tuning` — примеры для настройки; `validation` — отложенные примеры для проверки изменений. Комментарий объясняет, почему нужна именно такая реакция. Правило проверки действует на состояние канала после сообщения, а не на мгновенную реакцию сообщения в отрыве от прежних угроз. Сохраняется исходный текст; если он изменился, проверка потребует пересмотра примера.

**Критерии → Проверить все критерии на текущем результате** выводит несовпадения в панели пояснений. Слова и их сочетания, неоднозначность, отмены, направления и TTL настраиваются обычным редактором; критерии не вмешиваются в алгоритм.

Для времени между сообщениями добавьте в `criteria.json` критерий `at` с часовым поясом:
```json
{
  "at": "2026-10-05T14:41:10+03:00",
  "expected_level": 1,
  "expected_levels": {"kab": 1},
  "split": "validation",
  "note": "Не сокращать прежнюю тревогу при неизвестном новом положении"
}
```

Этот согласованный ранее пример уже добавлен в профиль monitor1654. Для радара пока нет утверждённой разметки. Нулевое число критериев означает, что точность не оценена.

Критерий сообщения задаётся `message_id`, например `monitor1654/158409`, вместо `at`. Типы: `rocket`, `kab`, `drone`, `unknown`. Значения уровней: 0–5 в системе основного приложения. Не задавайте одновременно `at` и `message_id`. Частичная проверка типов разрешена; для отсутствия типа явно задайте ему 0. Критерии вне выбранного диапазона не пропускаются молча: они дают несовпадение.

## Командная проверка для Codex и автоматических прогонов

```powershell
.venv\Scripts\python.exe -m src.channel_tuning check --profile profiles/monitor1654 --archives logs/telegram_monitor1654_2026-09-07_2026-10-07.jsonl --start 2026-09-07 --end 2026-10-07 --output test_results/channel_tuning/monitor1654 --split all
```

Даты включаются целиком, Europe/Kyiv. `--split tuning` проверяет настроечные примеры, `--split validation` — отложенные. Прогон восстанавливает контекст из доступной истории перед началом периода и учитывает истечение сроков между сообщениями. Сеть не используется.

Коды завершения:
- **0** — все выбранные критерии прошли;
- **1** — есть несовпадения;
- **2** — нет выбранных критериев либо ошибка входных данных.

Отчёт:
- `decisions.csv` — все сообщения, уровни, реакции и причины;
- `timeline.csv` — временная шкала, включая TTL между сообщениями;
- `summary.json` — результаты каждого критерия и контрольные суммы входов;
- `config_used.json`, `criteria_used.json` — точные настройки и критерии этого прогона;
- `review_template.json` — список сообщений для ручного разбора, не готовые правильные ответы;
- `REPORT.md` — пояснения.

Для создания дополнительного эксперимента:
```powershell
.venv\Scripts\python.exe -m src.channel_tuning init --profile profiles/experiment_monitor --channel monitor1654 --config profiles/monitor1654/config.json
```

Существующая непустая папка не перезаписывается. Копии экспериментальных профилей не означают дополнительные действующие Telegram-источники. Ограничение трёх источников относится к будущему рабочему серверу.

## Порядок моей настройки

1. Читаю профиль, архив и согласованные критерии.
2. Сохраняю исходную конфигурацию через механизм revisions, затем меняю словари и правила отдельного канала.
3. Сразу выполняю офлайн-прогон и разбираю несовпадения.
4. Проверяю отложенный набор, отмены, несколько целей, неоднозначность, направление вне города и потерю контекста.
5. Показываю изменения реакции на конкретных сообщениях и отчёт. Проверка нескольких размеченных примеров не считается полной оценкой качества месяца истории.

Изменение экспериментального профиля не является его включением в рабочий расчёт. Контроль подключения и применения профилей в живой системе будет частью серверного этапа.
