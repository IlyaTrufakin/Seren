# Основное приложение: первый этап эксплуатации по API

Запуск — прежний `run.bat` или `.venv\Scripts\python.exe main.py`. Программа использует настроенный API и существующий Modbus TCP-контур ПЛК. При запуске сохраняется прежнее автоматическое подключение к контроллеру; тестовые проверки выполнялись с подменой сетевых вызовов, реальный ПЛК не подключался.

## Что работает сейчас

- Основной модуль получает базовый уровень и типы от API.
- В нём нет словарей, групп дронов, поиска географических названий и прямого чтения Telegram.
- Все 12 правил и 14 звуковых профилей сохранены: отсутствие тревог, три степени для четырёх типов и потеря связи.
- Правила настраиваются по идентификаторам типов API, числовым уровням и при необходимости отдельным спискам уровней для каждого типа.
- В основном модуле четыре выходных состояния: нет угрозы, низкая, высокая, критическая. Для совместимости с действующей программой ПЛК внутренние коды остаются 0, 1, 2, 4; в настройках вместо кодов показываются названия состояний. Районные варианты 3/5 основной API-модуль не формирует.
- Явные типы КАБ/дронов/FPV уточняют air. Без уточнения air/3 считается ракетной угрозой, остальные уровни air — дроновой, согласно согласованной логике.
- Концепция объединения базы API и дополнительных угроз сохраняется в общем модуле композиции. Сейчас внешние источники не подключены, поэтому итог равен базе API. HTTP-сервер и приём состояний анализаторов не запускаются.

## Настройки

Откройте «Конфигуратор». Вкладки: API, Уровни по API, Звуковые профили, ПЛК, Тихий час. Справочник фактических типов и уровней API доступен в основном окне.

Новые рабочие настройки хранятся в `config_main.json`. При первом создании они переносятся из прежнего `config_threats.json`: параметры API, соответствия, включение API-правил, звуки, расписание, биты и обратная связь ПЛК. Telegram-условия в новые настройки не входят. Правила, ранее включённые исключительно для Telegram, при переносе не включаются для API автоматически. Звуки всех правил при этом сохраняются. Старый файл и профили анализаторов не перезаписываются.

После создания config_main.json его настройки самостоятельны: изменения config_threats.json больше не изменяют основной модуль.

## Общее время звукового профиля

Во вкладке «Звуковые профили» для каждого профиля добавлено **Общее время, с**:

- **0** — без ограничения; так перенесены все существующие профили, чтобы сохранить прежний режим.
- **1..86400** — максимальное время включения профиля в секундах.

Это время от первого разрешённого включения профиля в приложении, включая паузы между гудками и сериями. Оно не является суммой длительностей отдельных гудков и не отсчитывается от физического подтверждения включения реле. При отсутствующей связи с ПЛК таймер приложения продолжает идти.

Повторный ответ API с тем же профилем не сбрасывает таймер. Смена кода профиля сбрасывает отсчёт; возвращение к прежнему коду после другого профиля начинает новый период. Изменение источника или уровня, которое оставляет тот же выбранный профиль, не начинает звук заново.

При окончании общего времени приложение оставляет код профиля и передаёт количество гудков 0. Уровень тревоги и её типы сохраняются. В главном окне показаны заданное время, остаток либо факт окончания. В существующем проекте ПЛК звуковые серии управляют также синхронной лампой; прекращение серии прекращает эти импульсы, а передаваемые биты тревоги остаются активными.

Сохранение звуковых настроек не создаёт искусственного сбоя API: для прежнего API-адресата сохраняется актуальный снимок и отсчёт того же профиля. Новые параметры времени применяются к уже прошедшему времени. Тихий час подавляет звук и не перезапускает отсчёт уже включённого профиля. Если профиль впервые появился во время тишины, отсчёт начнётся при разрешении его звука. Перезапуск самого приложения создаёт новый отсчёт.

## ПЛК и проверка

Формат обмена сохранён: %MW0 — уровень/типы/heartbeat; %MW1 — обратная связь; %MW2..%MW6 — прежние пять параметров звука. Дополнительный регистр не требуется: общее время отсчитывает ПК. Частота обновления анализатора около 0,5 с, затем команда передаётся в очередном цикле Modbus; это определяет задержку остановки относительно заданной секунды.

Логика остановки при нулевом количестве гудков проверена на модели IL текущего файла Seren_Alarm.smbp. Проект ПЛК на этом этапе не изменялся; компиляция, загрузка и проверка физического реле не выполнялись. Если контроллер содержит другую версию программы, программная модель не подтверждает её поведение.

Проверки: 112 unittest-тестов, включая классификацию API, выходные уровни 1–5, отсутствие Telegram, таймер, повторные обновления API, смену профиля, сохранение настроек, потерю связи, передачу команды остановки и прекращение активной серии в модели ПЛК.


Упрощённый конфигуратор: в «Уровнях по API» выбираются галочки общей тревоги 1/2/3, КАБ 1/2, дрона 1/2 и FPV 1/2. Полей JSON и редактирования числовых выходных кодов нет. Явные КАБ и дроны соответствуют собственным правилам; общая тревога без уточнения относится к ракетным или дроновым правилам по ранее согласованной классификации. Невыбранные уровни не включают правило; при пересечении выигрывает более высокая степень. Звуковые профили и общий таймер сохранены.


## Бомбовое правило: два условия одновременно

Для каждой степени бомбовой угрозы выбираются общий уровень тревоги API 1/2/3 и уровень КАБ 1/2. Правило срабатывает, только если совпали оба условия. Например, общий 3 И КАБ 1 → критическая бомбовая угроза, если это выбрано для критического правила. Несколько галочек внутри одного условия означают ИЛИ. Между общим уровнем и КАБ используется И.

Без записи общей тревоги air выбранное бомбовое правило не срабатывает. Общая тревога сама по себе не выдаётся за КАБ: нужна запись kab-bombs. Если API содержит несколько общих уровней, используется максимальный, как в карточке API. При переносе старой конфигурации для КАБ разрешены общие уровни 1, 2, 3; затем их можно сузить в конфигураторе. Пустой выбор общего уровня не включает правило. Дроновые и ракетные соответствия сохраняют прежнюю логику.

## Журнал входных данных и решений

Подробный журнал: `logs/main_api_debug_YYYY-MM-DD.jsonl` (дата и время Europe/Kyiv). Каждая строка — отдельная запись:

- `api_poll`: каждый опрос, включая одинаковые ответы, отбой, некорректный ответ и ошибку соединения. В `input` сохранён полученный JSON-ответ, в `accepted_alarms` — последний принятый снимок; при ошибке он может быть прежним, поэтому учитывайте `api_error` и `output.api_online`.
- `decision`: изменение установленной степени/типов, выбранного правила, связи, блокировки или состояния звука, в том числе окончание общего таймера без нового ответа API.

В `output` указаны общая степень словами, внутренний код ПЛК, типы, правило, причина, общий входной уровень API и состояние звукового профиля. `bomb_conditions` содержит выбранные общие уровни, факт их совпадения и уровни КАБ для каждого бомбового правила. Ключ API и заголовок Authorization не записываются.

В основном окне «Системный журнал» показывает краткую строку входа и установленного уровня. Полный файл можно прислать для разбора либо читать как JSONL. Ошибка записи журнала не меняет вычисленную тревогу. Проверено 119 тестов, включая совместное условие КАБ, повторные опросы, входной JSON, ошибки связи и событие таймера.


Новое уточнение: дроновый тип только по явной записи дрона/FPV. Неуточнённый air/1–2 — общая воздушная тревога (внутренний тип unknown), air/3 без уточнения пока сохраняет прежнюю ракетную классификацию. Настроенные общие уровни перенесены из дроновых в отдельные общие правила; звуковой рисунок и ограничение времени сохранены при переносе. Нижняя карточка показывает только действительные уточнения API; при отсутствии отдельного типа и его уровня пишет «не указан API».


Актуальное правило по последнему указанию пользователя: любой air без явного уточнения типа (уровни 1, 2, 3) классифицируется как ракетный. Явные КАБ/дроны/FPV сохраняют приоритет. Неуточнённые общие уровни перенесены в ракетные правила соответствующей степени; существующие ракетные звуковые профили сохранены. В нижней API-карточке по-прежнему «не указан API», поскольку классификация приложения не является уточнением источника. main air_classification_version=3. Проверка: 121 тест пройден.


В дроновых правилах конфигуратора восстановлен выбор общего уровня 1/2/3. Теперь дрон и FPV работают как КАБ: общий уровень И выбранный уровень уточняющей угрозы должны совпасть. Общее условие сохраняется отдельно, поэтому air без уточнения остаётся ракетным. При переносе разрешены общие 1–3, затем выбор можно сузить.


## Уточнение ракетного типа — 2026-10-10

Неуточнённый air теперь означает общую воздушную тревогу, без ракетного бита.
Основной модуль отдельно читает event/type/rocket и event/type/ballistics. Ракетное
правило требует действующего air с выбранным общим уровнем и свежего сообщения,
адресованного выбранной территории или её родительской территории (иерархия ATU).
Срок установлен пользователем: 600 секунд от date сообщения. Повторный опрос его
не продлевает. global исключён. После срока/отбоя ракетное уточнение снимается;
общий уровень остаётся в соответствии с emergencies и настройками правил.
Явные КАБ/дроны могут действовать одновременно с ракетным уточнением.

Конфигуратор: rocket — общие уровни 1–3 + условие сообщения; unknown — общие
уровни 1–3 без уточнения; КАБ/дрон — прежнее И общего и типового уровня.
Срок и global находятся на вкладке API. У сообщений нет собственного числового
уровня: на нижней карточке это написано явно, для ракет применяется общий air.
Миграция версии 4 переносит прежние общие уровни и параметры звука в правила общей
тревоги, сохраняя отдельные коды профилей. Ракетные профили остаются настроенными.
Резервная копия: logs/config_main_before_explicit_rocket_2026-10-10.json.
Лог включает сообщения, подходящие уточнения, территории и ошибку чтения ленты.
Лента отдаёт последние десять сообщений каждого типа; уже полученные сообщения
хранятся до TTL, выпадение из окна последних сообщений не считается отменой.
Впервые запущенная программа не может восстановить сообщения за пределами этого окна.
Ошибка сообщений не отменяет работоспособный emergencies. Сохранённые сообщения
могут использоваться до api_stale_seconds без успешного чтения ленты, затем
применяются обычные правила общей тревоги/КАБ/дронов.
